## 一、harness 管什么、不管什么

判断一件事归谁，问三个问题：**它是动手干活吗？是定标准吗？是跨会话跨工具查落实/攒经验吗？**

harness 做四件事：

1. **定标准**——约束条文、质量门、知识的质量门/分类/生命周期规则。
2. **查落实**——CI 检查、配置漂移审计、约束生效统计。harness 不拦命令，但查拦截配置在不在。
3. **攒知识的家具**——知识的存储/检索代码（货架和账本），不含知识本身。
4. **治理流程**——约束的提案、退休、退化流程。

harness 不做三件事：

1. **执行面归 CLI**——沙箱、命令拦截、权限、网络管控是各家 CLI 的本职。CLI 现在弱的，等 CLI 迭代补齐，harness 不为弱 CLI 兜底。
2. **编排归 studio**——什么时候调机制、生产的东西往哪送、人审卡在哪插、活派给哪个 agent。
3. **应用内容归应用**——某个应用特有的约束条文和知识条目，归应用自己。

```
 ┌─────────────────────────────────────────────┐
 │  应用（如 studio 业务）                        │  应用特有内容：应用的活
 └─────────────────────────────────────────────┘
 ┌───────────┐        ┌───────────────────────┐
 │   CLI     │  执行面 │        studio         │  编排：什么时候调机制、
 │ 沙箱/拦截/ │ ◄────── │  编排 + 审卡中心 + 派单 │  人审卡在哪插、货往哪送
 │ 权限/网络  │        └───────────┬───────────┘
 └───────────┘                    │ 调用机制
                                  ▼
                    ┌───────────────────────────┐
                    │          harness          │  定标准 / 查落实 /
                    │  约束引擎·质量门·知识家具    │  攒知识的家具 / 治理流程
                    └───────────────────────────┘
```

推论：现有的命令黑名单拆两半——**黑名单条文（标准）留在 harness**，真正拦命令的钩子壳是**过渡件**，CLI 能力成熟就退役，不再给它加新功能。安全缺口分两种处理：CLI 原生能补的开开关；CLI 补不了的（如提交前机密扫描、依赖检查），harness 以"检查/门"的形式做——这是"查落实"，不越界。

## 二、约束怎么生、怎么死

约束分四类，判定一句话：**这条约束防的是外部风险、偷懒撒谎、做不到，还是体系自身？**

| 类 | 防什么 | 会退化吗 |
|---|---|---|
| 安全底线 | 外部风险（泄密、危险命令、外发） | 不过期，应是阻断级 |
| 诚信纪律 | 偷懒撒谎（不验证就说做完了） | 不过期——模型变强不变老实 |
| 能力兜底 | 做不到/忘了（文档同步之类） | **会退化**，模型强了就该退休 |
| 元约束 | 保护约束体系自身（治理段别被删） | 跟着 harness 走 |

**只有"能力兜底"会退化。** 安全底线的零拦截是好事，永不进退休候选。

```
 知识（攒的经验）── 同一教训反复出现 ──► 提案（人审卡，approve 才生效）
                                              ▼
                              应用层约束：存应用仓内，随 git 走，
                              改动过 PR；只能用填空式通用检查器
                                              │ 被证明够通用
                                              ▼ 升级提案：审卡发起 → harness 打包
                              通用层约束：harness 内置，    脱敏材料 → harness 仓 issue 评审
                              随包发布，所有项目共用
                                              │
                    能力兜底类随模型变强而退化：零拦截先进观察名单
                    挂一个季度（样本够 50 次再谈），人再决定退休
                                              ▼
                    退休 = 停用（不是删除，能恢复），
                    条文和原因沉淀成一条知识 ──► 回到知识库，循环闭合
```

退休保持人确认，工具只摆数据。确认收口在 studio 审卡中心：approve 后由 studio 调 harness 执行退休、自动提交代码库、触发检索同步；回滚不改历史，写一条"重新启用"的新条目。

## 三、知识怎么流转

知识是攒下来的经验条目（模式、教训、决策），越攒越值钱，不过期。**家具归 harness，货归 studio**：存储/检索代码是 harness 的家具；知识条目本身和"生产、审、同步、消费"的编排永远归 studio，存在 `~/.studio/knowledge`（唯一正本），不回填 harness。

```
 生产 ──► 人审 ──► 存（家具归 harness，货在 ~/.studio/knowledge）
 (studio  (审卡中心)        │
  7 类来源)                ├──► 频道注入：agent 干活时按频道直接查文件，挑条目进 prompt
                           │    （不经过向量库）
              同步触发      │
              （studio）    ▼
                        向量库 ──► 语义检索：studio 界面搜索 + CLI 会话查询
                                   （现任工具是 mcp-local-rag，归 studio 编排，
                                     harness 不认识它）
```

**频道注入和语义检索是两条独立通道**，不是串成一条链的两段。harness 里目前有个做注入编排的部件（KnowledgeInjector）长错了地方，长期挪去 studio；"知识该不该升级成约束/skill"的候选判定留在 harness（那是标准），提案落到 studio 审卡。

## 四、安全底线补齐清单

推导逻辑：**只补不可逆损失面**（机密进了 git/外发、危险命令、依赖投毒；可逆的改错代码 git 能恢复，不配专门防线）。每项的归属：CLI 本职接得住的 → 开 CLI 原生开关；CLI 管不着的 → harness 以标准+检查补；个别 CLI（kimi）能力缺口的 → 不兜底、不做派单干预（一视同仁），残余风险由 studio 侧统一控制承接。

P0（开关没开/级别没调/现成没接，成本最低收益最大）：

| 1 | 凭证扫描从警告级升阻断级 | harness 通用层 | 机密进 git |

| 4 | ~~高危任务不派 kimi~~ **已撤销**（ADR-0031 修订：不做派单干预，一视同仁；能力快照会烂） | — | — |

## 五、人审统一收口 + UI 禁黑话

**所有需要人拍板的事统一收口到 studio 审卡中心**：知识提案、约束退休确认、新约束提案、应用层升级通用层提案，走同一个界面同一套卡。harness CLI 的交互确认只是裸项目（没有 studio 的场景）的备用通道。

**审卡 UI 禁黑话是硬要求**：摆给人看的统计必须翻译成人话——写"3 个月评估 60 次，拦到 0 次"，不写"零拦截、样本≥50"这类行话。实施时按此验收。
