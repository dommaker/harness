# ADR-0031: harness 第一性定位与分工——四件事、三不做、CommandGate 拆分

- 日期：2026-09-22
- 状态：已接受
- 关联：wayfinder 地图 `/root/projects/docs/wayfinder/harness-repositioning/`（锁定前提，票 03/04/06/08/09 定案）；ADR-0001（约束体系起点，本 ADR 给它补上定位层面的"为什么"）；ADR-0029（harness 收编为机制与知识工具的方向裁决，本 ADR 将其上升为第一性分工）；ADR-0032/0033/0034（本 ADR 的展开）

## 背景

harness 从 42 条约束删到 7 条、关停文本注入层（ADR-0029）之后，"harness 到底管什么"一直没有一份明确定义，用户体感痛点就是职责不清楚、后续流程不清楚。实践中的模糊点集中在三处：CommandGate 的 hook shim 直接拦命令，越进了 CLI 的执行面；安全缺口面前没有"谁该补"的判定尺（票 01 盘点：越权写/网络外发/依赖投毒基本空白）；各 CLI 原生安全能力差异大（票 09 实测：codex 默认真沙箱，claude 能力全但默认关，kimi 只有软控制），harness 要不要为短板 CLI 兜底没有结论。

## 决策

1. **三问定归属**：一件事归谁，问三个问题——它是动手干活吗（执行）？是定标准吗？是跨会话跨工具查落实/攒经验吗（治理）？
2. **harness 做四件事**：定标准（约束条文、质量门、知识质量门/分类/生命周期）、查落实（CI 检查、配置漂移审计、约束生效统计）、攒知识的家具（存储/检索代码，不含知识数据）、治理流程（提案/退休/退化）。
3. **harness 不做三件事**：执行面（沙箱/命令拦截/权限/网络管控——CLI 的职责，等 CLI 迭代补齐）；生产编排（studio 的活）；应用特有内容（应用的活）。
4. **CommandGate 拆分**：黑名单条文是标准，留在 harness；`pretool-use-hook.js` 这个拦命令的 shim 是**过渡件**，CLI 原生执法面成熟即退役。过渡期不给 shim 加功能（票 08 P1-7：审计留痕走已有的 traces 通道，不动 shim）。
5. **不为弱 CLI 兜底**：kimi 无沙箱、无网络管控、hooks fail-open，这些缺口 harness 不接手，由 studio 用派单策略管理残余风险（高危任务不派 kimi，属风险管理不是安全机制）。
6. **安全缺口的归属判定**：CLI 原生能补的，开开关（codex 沙箱+断网+env 过滤、claude 沙箱类）；CLI 管不着的（凭证进 git、全历史扫描、依赖投毒、发布链），harness 以"标准+检查/门"的形式做——这是"查落实"，不构成对执行面的越界。

## 否决的备选

- **harness 全量兜底 CLI 短板**：被否决。一旦 harness 接下执行面，shim 就从过渡件变成永久件，永远没有退役方向；且每家 CLI 短板不同，兜底等于在 harness 里重造一套跨 CLI 沙箱，与"等 CLI 迭代"的现实趋势对着干（票 09：codex 默认已有真沙箱，claude 只是没开）。残余风险用派单管理，不用机制硬填。
- **harness 纯机制、零内容**：被否决。"定标准"必然含内容——内置约束条文、命令黑名单条目本身就是内容，把它们推给每个项目各自维护，结果是安全条文到处重抄、水平参差。正确的切分不是"机制 vs 内容"，而是"通用内容归 harness 内置，应用特有内容归应用"（见 ADR-0033 两层模型）。

## 影响

- 分工判定有了统一尺子，后续归属争议先过三问。
- CommandGate shim 冻结新功能，退役条件 = 目标 CLI 原生执法面覆盖 block 级拦截；黑名单条文（harness 标准）不受影响，继续维护（票 08 P1-6 补 git 破坏类条目）。
- 安全底线补齐按票 08 的 P0/P1/P2 清单执行，实施另起 effort；执行面缺口列给 CLI 迭代等齐，不进 harness  backlog。
- studio 侧承接：派单策略（高危不派 kimi）、codex 沙箱/env 开关、hook matcher 补全，均为 studio 编排层改动，不在本仓。
