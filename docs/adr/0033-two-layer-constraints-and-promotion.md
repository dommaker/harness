# ADR-0033: 两层约束模型——应用层存仓内随 git、填空式 checker、升级走审卡 + 仓 issue

- 日期：2026-09-22
- 状态：已接受
- 关联：wayfinder 地图 `harness-repositioning/`（锁定前提"约束分两层"，票 04 细化定案）；ADR-0001（注册表闭环语义是"不许自带 checker"的机制基础）；ADR-0029（severity 分级与退休机制对应用层一视同仁的前提）；ADR-0031（分工：应用特有内容归应用）、ADR-0032（四分法与退休口径）

## 背景

锁定前提已定"约束分两层：通用层（harness 内置）+ 应用层（应用自长，经注册接口交 harness 引擎执行），应用层被证明通用后才提案进通用层"，但形态未定：应用层约束存哪、checker 怎么写、执行面是否和通用层一样、升级通道怎么走、和知识链路怎么双向打通。ADR-0029 连带退役了 custom-constraints.yml（其唯一执行语义是文本注入），应用层需要一个新的、不依赖文本注入的承载形态。

## 决策

1. **应用层约束存应用仓内**（`.harness/` 下的文件，随 git 走）：改约束过 PR，CI 可查。不进 `~/.studio` 数据区——约束是项目纪律，改动不能绕开 git 评审。
2. **checker 只用 harness 提供的"填空式"通用 checker**（正则扫描、文件存在性、命令黑名单等参数化模板），应用层约束填参数即可用，**不允许项目自带 checker 代码**。需要新 checker 的约束说明它够通用，直接走升级提案进通用层。
3. **执行面一视同仁**：应用层约束可用 check / CI / report / retire 全套机制，severity 分级、观察名单、退休沉淀语义与通用层相同（ADR-0032 的四分法与退化口径同样适用）。
4. **升级通道（应用层 → 通用层）**：发起和初审在 studio 审卡中心（与知识提案、退休确认同一界面）→ approve 后由 harness 出的打包工具生成脱敏提案材料（条文 + checker 配置 + 使用统计）→ 人拿材料去 harness 仓开 issue → 维护者评审，随 harness 发版进内置。
5. **知识 → 约束的触发点**：复用 harness 生命周期面的候选判定机制（checkSkillCandidate 同类：同一教训反复出现则候选成约束），提案落 studio 审卡。反向（约束退休 → 沉淀成知识）已由退休流程承载（ADR-0032），两个方向闭环。
6. **审卡 UI 禁黑话（硬要求）**：统计数据必须翻译成人话（"3 个月评估 60 次拦到 0 次"，不写"零拦截、样本≥50"）。此要求约束所有审卡形态（退休确认、升级提案、知识提案），实施时验收。

## 否决的备选

- **应用层约束存数据区（`~/.studio`）**：被否决。约束是项目纪律，存数据区意味着改约束不过 git、不留评审痕迹，CI 也读不到——与"查落实"的基本要求直接冲突。
- **允许项目自带 checker 代码**：被否决。自带代码意味着任意应用代码进入 harness 引擎执行面，审查面和安全面都不可控，也架空 ADR-0001 的注册表闭环（kind='check' 必须有注册 checker）。填空式模板覆盖了现有全部需求形态；真需要新检查能力，说明它够通用，走升级通道进通用层是正确出路。
- **升级提案纯手写 PR**：被否决。手写提案没有脱敏处理（可能带出应用内部信息），也没有使用统计（拦了多少次、误报多少），维护者评审无据可依。打包工具统一出材料，是提案质量的前置保障。

## 影响

- harness 需要新增：应用层约束的注册接口与 `getEffectiveConstraints` 合并逻辑、填空式通用 checker 集、升级提案的脱敏材料打包工具。
- studio 需要新增：审卡中心的约束提案卡与升级提案卡（含人话统计渲染，禁黑话验收）。
- custom-constraints.yml 不复活；应用层的承载形态以本 ADR 为准。
- 实施另起 effort，本 ADR 只定形态。
